# 复合中文指标分析整改设计

## 背景与问题

真实上传 `财务分析样例数据.xlsx` 后，问题“分析 2024-01 到 2025-12 的营业收入、毛利率和营业利润趋势，指出异常月份及可能原因，并引用数据证据。”返回 `INSUFFICIENT_DATA`。根因是当前 `AnalysisPlan` 只能承载一个算子和一组字段：问题含“异常”时被压缩为单异常算子，多个中文指标无法同时匹配，也不能把明细中的分子、分母计算为派生比率。

## 目标

支持一个用户问题包含多个高置信中文指标、趋势、异常和数据内原因线索时，生成可验证的直接回答。每一个数值、异常和原因线索均可回溯到同一受控计算链路与证据。对缺字段、低置信度和不支持的需求保持保守拒答。

## 非目标

- 不使用 LLM 生成计算或数字。
- 不根据文件名、地区、营收等固定业务模板切换逻辑。
- 不自动进行跨表 join；本次原因线索只取分析主表内字段。
- 不实现预测、库存风险等尚无白名单执行器的能力。

## 设计

### 1. 复合计划

新增 `CompositeAnalysisPlan`，包含一个统一主表、问题、整体状态、限制和按用户问题顺序排列的 `MetricAnalysisPlan`。一个指标子计划包含：指标名称、时间字段、计算定义、趋势算子、异常算子、字段置信度和可选原因上下文。

既有单指标 `AnalysisPlan` 保留给排名、比较、相关等简单问题。`build_plan()` 在检测到多个请求指标且同时存在趋势/异常意图时返回复合计划；简单问题继续返回原类型，避免破坏现有调用者。

主表选择必须满足所有可执行子计划的高置信字段，优先选择同时含时间字段、原始指标字段和可用上下文的表。若一个请求指标无法安全映射，整体结果为 `PARTIAL`，并列出未映射指标；若没有任何指标可映射，返回 `INSUFFICIENT_DATA`。

### 2. 指标定义

指标从问题中的字段名或通用语义词匹配到 Profile 中置信度不低于 0.70 的字段。直接指标使用单列按时间聚合的 `sum`。派生比率只在问题请求“率/比率/margin/rate”且同表可高置信找到分子与分母时计算：先按时间分别求和，再相除。

对于样例的毛利率，定义为 `sum(毛利（万元）) / sum(营业收入（万元）)`；不得对明细行毛利率做平均。派生定义必须写入 calculation evidence。

### 3. 统一时间趋势与异常

每个子计划先按可信时间字段聚合成时间序列。趋势 finding 包含全周期时间点、起点、终点和聚合公式。异常 finding 对时间序列的相邻变化率使用 IQR 检测；输出异常时间点、当前值、前期值与环比变化率。若离散度不足或无异常，结论必须如实说明，不伪造异常月份。

### 4. 原因线索

仅在主表内查找高置信文本/维度上下文：字段名含 `备注`、`说明`、`原因`、`comment`、`note` 等通用注释语义时，按异常时间聚合其非空、去重文本，作为“可能原因的同月备注证据”。

同时可从同表其他数值字段生成“同期联动线索”：只展示异常期与前一期相比变化显著的字段及其值，不称其为因果。没有备注和可用数值线索时，finding 明确说明“数据未提供可验证的原因线索”。

### 5. 校验与响应

复合执行结果必须复用现有 validator。每条 finding 必须有文件 hash、表、字段、过滤、计算、输出、行索引和置信度；派生率还必须记录分子、分母。回答由所有已验证 findings 的结论和限制拼接产生，不能由模板或 LLM 额外补数。

现有 API 生命周期仍为 `status: succeeded`；分析结论使用独立 `validation_status: SUCCESS/PARTIAL/INSUFFICIENT_DATA`。前端沿用现有 findings/evidence 渲染路径。

## 验收测试

1. 以等价的财务明细工作簿测试三指标：营业收入、毛利率和营业利润各有趋势 finding；毛利率公式是月度聚合后相除。
2. 2025-03 的异常 finding 有时间、前期值、环比变化、备注“需求回落：销量下滑”和销量/单价等同月联动证据。
3. 缺少备注或上下文时，原因区明确数据不足，不出现臆测性原因。
4. 非标准中文/英文指标字段只在 Profile 高置信匹配时计算；无法匹配的指标不产生数字。
5. 真实上传 API 使用 `F:\财务分析样例数据.xlsx` 运行原问题，必须返回 `succeeded`、至少 `PARTIAL`，包含三个趋势、异常结论和证据。
6. 完整后端、前端测试、生产构建、编译检查与差异检查通过。
