# 通用数据分析与决策支持 Agent 设计规格

日期：2026-08-29

状态：待用户复核

## 1. 目标

将当前以 Dify 工作流设想为主、尚无产品实现的项目，收敛为一个可本地运行的通用数据分析与决策支持工作台。用户上传一个或多个 Excel 或 Word 文件，用自然语言说明目标；系统读取真实内容、提出可执行分析计划、在用户确认后执行分析，并输出可追溯的风险与方案权衡建议。

首版的重点不是图表数量或通用 Notebook 编辑器，而是让每条建议都能回答：它依据了哪些文件和数据、风险来自哪里、有哪些可执行方案、各方案的收益/成本/潜在损害是什么、哪些结论仍需要人工确认。

## 2. 产品边界

### 2.1 支持的通用能力

- 上传 XLSX、XLS 和 DOCX；单次 1--5 个文件。
- 完整读取表格、工作表、字段、文本段落和 Word 表格，并报告读取范围与失败项。
- 根据用户目标生成分析计划，计划包含输入、方法、预期产物和限制；用户确认前不执行生成代码。
- 对结构化数据执行描述统计、趋势/分组/相关性分析、异常检测、缺失与重复检查和可视化。
- 从 Word 中提取事实、规则、约束、风险描述和表格；不能把 Word 的自然语言当成已验证数据。
- 基于真实执行结果输出风险登记册与方案比较，不把模型推测伪装成文件事实。
- 生成图表、结果表、Markdown 报告和结构化 JSON 结果；图表服务于证据解释，不作为主要目标。

### 2.2 不承诺的能力

- 不把通用风险评分当作医疗、法律、金融、化工、工程安全等领域的专业结论。
- 不在没有明确关联字段或用户确认的情况下自动合并文件。
- 不允许模型生成的代码访问宿主机、Docker Socket、私密环境变量或默认外网。
- 不允许模型直接执行任意 shell、包安装命令或网络请求。
- 首版不实现长期驻留 Jupyter Kernel、协作编辑、正式发布链接或自动安装任意依赖。

## 3. 核心用户流程

1. 用户上传 Excel/Word 文件。
2. 文件服务生成 `file_id`、SHA-256、类型、大小和解析概览；界面展示每个文件是否完整读取。
3. 用户显式勾选本次分析使用的文件，并输入目标，例如“找出交付延期原因并比较三个改进方案”。
4. 规划 Agent 仅使用所选文件的解析概览，返回可编辑的分析计划：问题拆分、数据质量检查、拟用方法、需要人工确认的假设和预期产物。
5. 用户选择“执行计划”或“返回修改”。未经该选择不得生成或运行分析代码。
6. 执行器在隔离环境中运行受控 Python 分析，产出真实表格、统计量、图表、日志和数据血缘。
7. 评估 Agent 只读取执行结果、结构化风险规则和用户目标，输出事实、推断、风险、方案和复核项。
8. 用户可要求“解释证据”“修改分析计划”或“比较其他方案”；每次重新执行创建新修订，旧结果保持可查看。

## 4. 系统架构

```text
Web 工作台
  ├─ 文件与任务 API
  ├─ 计划确认界面
  └─ 结果、风险与方案比较界面
        ↓
任务编排服务
  ├─ 文件解析器（Excel / Word）
  ├─ Dify 规划与解释适配器
  ├─ 受控分析代码生成器
  └─ 结果规范化与修订管理
        ↓
隔离执行器
  ├─ 只读输入文件映射
  ├─ 预装数据分析依赖
  ├─ 默认断网、CPU/内存/时间限制
  └─ 结构化产物与运行日志
```

Web 工作台不执行用户或模型代码。Dify 负责计划、解释和受控 JSON 结构的生成，不直接接收完整原始文件或拥有执行器权限。执行器是唯一能读取完整文件并计算事实的组件。

## 5. 文件与证据模型

### 5.1 文件解析

- Excel：枚举所有可读工作表，记录行列数、字段、类型推断、缺失值、重复值、异常值候选、公式/合并单元格/隐藏表信息。
- Word：提取段落、标题层级、表格和图片计数；表格转换为独立结构化数据集；段落保留来源位置。
- 每个解析结果绑定 `file_id` 与 SHA-256；分析代码只能通过 `FILES[file_id]` 读取。
- 文档文本中的数字、规则和结论均标记为“文档陈述”，除非被执行结果或另一来源验证。

### 5.2 证据等级

| 等级 | 含义 | 在报告中的标签 |
| --- | --- | --- |
| A | 执行器从已选文件直接计算或提取 | 文件事实 |
| B | A 级事实经明确方法推导 | 数据推断 |
| C | 用户明确提供的业务前提 | 用户前提 |
| D | 模型提出、尚未验证的解释或建议 | 待验证建议 |

最终结论必须携带至少一个 A/B/C 级来源；仅有 D 级来源的内容只能列入“待验证假设”。

## 6. 通用风险与方案评估

### 6.1 风险登记册

每个风险项采用固定结构：

```json
{
  "risk_id": "R-001",
  "title": "交付日期集中延后",
  "category": "进度",
  "evidence": [{"artifact_id": "...", "level": "A", "summary": "..."}],
  "likelihood": {"level": "high", "basis": "..."},
  "impact": {"level": "medium", "basis": "..."},
  "controllability": {"level": "medium", "basis": "..."},
  "uncertainties": ["缺少资源投入字段"],
  "human_review_required": false
}
```

风险等级不是跨行业通用的绝对概率。它是基于当前数据的相对优先级，计算规则和依据必须显示。对于医疗、法律、金融、危化、人身安全或用户标为关键的场景，`human_review_required` 强制为 `true`，并禁止输出“可直接执行”的专业处置结论。

### 6.2 方案比较

每个方案必须明确：行动步骤、预期收益、成本/资源、潜在损害、适用前提、风险缓解方式、证据和验证指标。推荐策略使用可解释的多目标排序：优先满足硬约束，再比较预期收益、潜在损害、实施成本和不确定性；不允许以单一“总分”掩盖权衡。

默认输出三类方案：保守方案、平衡方案、进取方案。若数据或业务约束不足以支持三种不同方案，系统明确说明，而不虚构方案。

## 7. Dify 与 Agent 分工

- 固定链路（上传、解析、校验、计划确认、执行、产物归档）使用后端服务/Workflow。
- 需要选择分析方法、解释异常、提出替代方案和依据用户反馈迭代时使用 Agent。
- Agent 输入仅包括：用户目标、已选文件概要、数据字典、执行结果摘要、风险结构化规则和上一次结果；完整文件始终留在执行器内。
- Agent 输出采用 JSON Schema 校验。代码生成器只接受受限操作清单，例如 pandas 读取、聚合、统计、受批准的 matplotlib/plotly 图表；不接受自由 Python 或 shell。

## 8. 修订与可追溯性

- 每次计划、执行与结果生成均创建 `revision_id`。
- 每个产物记录 `file_id[]`、分析计划、代码快照、运行日志和修订号。
- 失败执行不能替换最近成功修订。
- 用户要求修改时先显示将重用的文件与假设；文件选择变化时必须创建新的选择快照和修订。

## 9. 首版验收标准

1. 上传一个 XLSX 或 DOCX 后，界面准确展示文件读取结果；损坏文件被标记且不能继续分析。
2. 用户明确选择文件和目标后，系统生成可读、可编辑的分析计划；未确认计划时没有执行器运行记录。
3. 对含数值字段的 Excel，执行器能够产出至少一张基于真实数据的图表、一张结果表和完整运行日志。
4. 对 Word，系统能区分提取的文本/表格与经过执行计算的结论。
5. 每份结果报告将“文件事实、数据推断、用户前提、待验证建议”分开呈现。
6. 至少一条风险项包含证据、可能性、影响、可控性、不确定项和人工复核标志。
7. 方案比较至少包含收益、成本、潜在损害、前提和验证指标；证据不足时明确提示，不能伪造量化结果。
8. 未明确关联字段时，两个上传文件不会自动合并。
9. 执行环境默认无法访问外网、宿主机、Docker Socket 和宿主环境变量。
10. 修改目标或计划后生成新修订，旧修订仍可查看且结果不被覆盖。

## 10. 分阶段实施范围

第一阶段仅实现单次任务的完整闭环：Excel/Word 上传与解析、文件选择、计划确认、受控分析执行、证据化风险/方案结果和基本历史修订。第二阶段再考虑多文件关联、报告导出、自动修复、可视化编辑和更复杂的权限/部署需求。
